## Цель работы

Реализовать учебный прототип системы **банковских переводов между шардами**, в котором атомарность распределенной операции обеспечивается протоколом **Two-Phase Commit (2PC)** поверх **durable Write-Ahead Log (WAL)**.

Перевод между двумя счетами на разных шардах состоит минимум из двух локальных операций: `DEBIT` на одном шарде и `CREDIT` на другом. Локальный ACID не гарантирует, что обе операции либо применятся, либо не применятся: сбой сети или процесса легко приводит к ситуации «деньги списали, но не зачислили». 2PC превращает ненадежную сеть и частичные сбои в **единое решение COMMIT/ABORT**, а WAL делает это решение **переживающим перезапуск процесса**.

В результате должны получиться:
1. Координатор и участники как **отдельные процессы**, общающиеся по TCP (JSON Lines).
2. State machine участника `INIT → PREPARED → COMMITTED/ABORTED` с правильной идемпотентностью.
3. **Durable WAL на диске** у координатора и каждого участника. Инвариант **log-before-reply / log-before-broadcast** строго соблюдается.
4. Корректное поведение после **реального падения процесса** (`kill -9` или `System.exit`): после повторного запуска с тем же `--data-dir` процесс читает свой WAL и доводит начатые транзакции до конца.
5. Демонстрация **blocking problem** 2PC — фундаментального ограничения протокола, которое в этой ДЗ нужно показать, а не решить.

> HW6 — **новый репозиторий**, не расширение HW2–HW5. В предыдущих ДЗ решалась задача репликации (одни и те же данные на разных узлах). Здесь — задача атомарности изменений на узлах с **разными** данными, переживающая падения.

## 1. Что требуется и что не требуется

**Требуется:**
- 1 процесс координатора + минимум **3 процесса-участника** (3 шарда);
- TCP-соединения, JSON Lines, отдельные процессы, у каждого свой `--data-dir`;
- 2PC: фазы Prepare и Commit/Abort, голосование, ретраи, таймауты;
- WAL в файлах на диске у координатора и у каждого участника, по одной папке на ноду;
- балансы и брони участника **полностью восстанавливаются из WAL** при старте процесса;
- реальное падение процесса (`System.exit` / `kill -9`) и его повторный запуск;
- управляемые задержки на критических точках протокола (для воспроизведения сценариев);
- 8 обязательных демо-сценариев;
- бенчмарки и `report.md`.

**Не требуется:**
- внешние библиотеки (Zookeeper, etcd, фреймворки, БД) — только стандартная библиотека Java;
- 3PC, Paxos Commit, любые усложнения протокола;
- автоматический `failure detection` координатора участниками: участник в `PREPARED` ждет указаний и не пытается сам выбрать исход.

## 2. Архитектура

В системе три типа процессов:
1. **Coordinator** — один процесс, точка входа для команды `transfer`. Хранит свой WAL в `<data-dir>/coordinator/wal.log`.
Шлет `PREPARE`, собирает голоса, рассылает `COMMIT/ABORT`.
2. **Participant (Shard)** — отдельный процесс на каждый шард, минимум 3 шарда (`shardA`, `shardB`, `shardC`).
Каждый держит балансы своих счетов в памяти и пишет свой WAL в `<data-dir>/<shardId>/wal.log`.
3. **CLI** — консольное приложение для управления. Должен быть отдельным процессом, который общается с Coordinator-ом по TCP.

Раскладка счетов «счет → шард» детерминированная и заранее известна координатору и CLI. Можно использовать `hash(account) % shardCount` или явную таблицу из конфига.

Перевод `transfer alice bob 100` декомпозируется координатором в план:
```
shardA: DEBIT  alice 100
shardB: CREDIT bob   100
```

Координатор и участники запускаются независимо, у каждого свои параметры запуска: идентификатор, порт, путь к директории данных, адреса шардов (для координатора).
Структура папки данных:
```
data/
  coordinator/wal.log
  shardA/wal.log
  shardB/wal.log
  shardC/wal.log
```

Перезапуск процесса с тем же `--data-dir` — это и есть recovery. Никаких отдельных «recover»-команд CLI не предусмотрено.

## 3. Модель данных

### 3.1. У участника (in-memory, восстанавливается из WAL)
```text
balances:     Map<String, Long>             // account -> balance
reservations: Map<TxId, Reservation>        // активные брони для DEBIT
records:      Map<TxId, ParticipantRecord>  // состояние по txId
```
```text
Reservation       { account: String, amount: Long }
ParticipantRecord { state: ParticipantState, operation: String }
ParticipantState  ∈ { INIT, PREPARED, COMMITTED, ABORTED }
```

### 3.2. У координатора (in-memory, восстанавливается из WAL)
```text
plans:  Map<TxId, TxPlan>     // план транзакции (кто что делает)
states: Map<TxId, TxState>    // BEGUN / DECIDED_COMMIT / DECIDED_ABORT
```
```text
TxPlan: List<(participantId, operation)>
operation: "DEBIT <account> <amount>" | "CREDIT <account> <amount>"
```

### 3.3. Логика prepare для счетов
- `CREDIT` — всегда vote=COMMIT (зачисление в учебной модели «всегда возможно»);
- `DEBIT` — vote=COMMIT, если `balance(account) - sum(active_reservations(account)) >= amount`. Иначе vote=ABORT.
При vote=COMMIT создается `Reservation(txId, account, amount)`;
- на `commit` для DEBIT: списать `amount` с `balance` и снять `Reservation`. На `abort` для DEBIT: только снять `Reservation`.

## 4. WAL

### 4.1. Файлы и формат
WAL у каждой ноды — это **append-only файл `wal.log`** в ее папке данных. Каждая запись — отдельная строка в формате JSON (JSON Lines).

**WAL координатора:**
```
{"txId":"a1b2","event":"BEGIN","plan":[{"node":"shardA","op":"DEBIT alice 100"},{"node":"shardB","op":"CREDIT bob 100"}]}
{"txId":"a1b2","event":"DECISION","decision":"COMMIT"}
```

**WAL участника:**
```
{"txId":"a1b2","event":"PREPARED","operation":"DEBIT alice 100"}
{"txId":"a1b2","event":"COMMITTED","operation":"DEBIT alice 100"}
```

Возможные ивенты у координатора: `BEGIN`, `DECISION`. У участника: `PREPARED`, `COMMITTED`, `ABORTED`.

`operation` дублируется в `COMMITTED` и `ABORTED` намеренно: replay тогда проходит за один линейный проход по файлу без второго прохода для поиска связанных записей.

### 4.2. Правила записи (обязательны)
1. Запись делается одним append-операцией (`Files.writeString(..., CREATE, WRITE, APPEND)`) с `\n` на конце.
2. **Запись в WAL должна завершиться до соответствующего сетевого действия:**
   - `VOTE_COMMIT` отправляется только после того, как `PREPARED` уже записан в файл;
   - `COMMIT/ABORT` рассылается только после того, как `DECISION` уже записан в файл;
   - `ACK` об успешном `COMMIT/ABORT` отправляется только после того, как `COMMITTED/ABORTED` уже записан в файл.


### 4.3. Что НЕ хранится на диске
Балансы, брони и in-memory `records` процесса **не персистятся отдельно**.
Они полностью восстанавливаются replay'ем WAL.
Это ключевая идея durability: единственный источник истины — WAL, все остальное — производная.

## 5. Сетевой протокол

### 5.1. Транспорт и формат
- TCP-сокеты;
- JSON Lines (1 JSON на строку, разделитель `\n`);
- допустимо принимать все на одном порту и различать по полю `type`.

### 5.2. Типы сообщений

**CLI → Coordinator:** `CLIENT_TRANSFER`, `CLIENT_BALANCE`, `CLIENT_LIST_TX`, `CLIENT_TX_LOG`, `CLIENT_CLUSTER_DUMP`, `CLIENT_SET_BALANCE`, `CLIENT_SET_DELAY`, `CLIENT_ARM_CRASH`.

**Coordinator → Participant:** `PREPARE` (`{txId, operation}`), `COMMIT` (`{txId}`), `ABORT` (`{txId}`).

**Participant → Coordinator:** `VOTE` (`{txId, vote}`), `ACK` (`{txId, kind}`).

**Participant → Coordinator (recovery-time):** `STATUS_QUERY` (`{txId}`) ← `STATUS_RESPONSE` (`{txId, decision: COMMIT|ABORT|UNKNOWN}`).

### 5.3. Ретраи и таймауты
- RPC координатора (`PREPARE`, `COMMIT`, `ABORT`) имеют таймаут (1–2 сек по умолчанию) и фиксированное число ретраев (3 по умолчанию);
- параметры таймаута и числа ретраев настраиваются через CLI: `setRpcTimeout <ms>`, `setRpcRetries <n>`;
- на фазе 1 таймаут после всех ретраев → safety-first ABORT;
- на фазе 2 таймаут → продолжать ретраить; если не получилось доставить, после рестарта координатора recovery возьмет на себя.

### 5.4. Идемпотентность
Любое сообщение протокола идемпотентно по `txId`:
- повторный `PREPARE` в `PREPARED` → снова `VOTE_COMMIT`;
- повторный `PREPARE` в `ABORTED` → снова `VOTE_ABORT`;
- повторный `COMMIT` в `COMMITTED` → no-op + ACK;
- повторный `ABORT` в `ABORTED` → no-op + ACK.

Идемпотентность критична: после рестарта координатор будет пере-рассылать решения участникам, которые могли уже их применить.

## 6. State machine участника

### 6.1. Таблица переходов

| Состояние   | PREPARE                                                                                                                 | COMMIT                                                      | ABORT                                                 |
|-------------|-------------------------------------------------------------------------------------------------------------------------|-------------------------------------------------------------|-------------------------------------------------------|
| `INIT`      | вызвать локальный prepare. Если ok → **WAL `PREPARED`**, → `PREPARED`, vote=COMMIT. Если нет → vote=ABORT, → `ABORTED`. | протокольная ошибка → игнор                                 | no-op                                                 |
| `PREPARED`  | vote=COMMIT (идемпотентно)                                                                                              | применить операцию, **WAL `COMMITTED`**, → `COMMITTED`, ACK | освободить бронь, **WAL `ABORTED`**, → `ABORTED`, ACK |
| `COMMITTED` | vote=COMMIT                                                                                                             | no-op + ACK                                                 | протокольная ошибка → игнор                           |
| `ABORTED`   | vote=ABORT                                                                                                              | протокольная ошибка → игнор                                 | no-op + ACK                                           |

### 6.2. Инварианты (проверяются на защите)
1. `VOTE_COMMIT` отправляется **только после** того, как `PREPARED` оказался в WAL на диске.
2. `COMMIT/ABORT` рассылается **только после** того, как `DECISION` оказался в WAL координатора на диске.
3. `ACK COMMITTED/ABORTED` отправляется **только после** того, как `COMMITTED/ABORTED` оказался в WAL участника на диске.
4. Участник в `PREPARED` **никогда не выбирает исход самостоятельно**. Если координатор недоступен — участник ждет. Это и есть blocking problem.

## 7. Recovery

### 7.1. Recovery — это рестарт процесса
В этой ДЗ нет отдельных команд CLI вроде `recoverCoordinator`.
Recovery срабатывает **автоматически при старте процесса**: если в `data-dir` уже есть непустой `wal.log`,
процесс его читает и доводит дело до конца, а затем продолжает обслуживать новые запросы.

### 7.2. Старт координатора
1. Прочитать `<data-dir>/coordinator/wal.log`. Если файла нет — старт «с нуля».
2. Сгруппировать записи по `txId`, восстановить `(plan, decision?)`.
3. Для каждой `txId` с зафиксированным `DECISION` → дослать `COMMIT`/`ABORT` всем участникам из `plan` (с ретраями).
4. Для `txId` с `BEGIN`, но без `DECISION` → политика **safe abort**: дописать `DECISION=ABORT` в WAL и разослать `ABORT`. Это размораживает зависших участников; политика консервативная, но безопасная.
5. После завершения roll-forward координатор начинает обслуживать новые `CLIENT_TRANSFER`.

> Никаких новых `txId` в recovery не создается. Recovery «дотягивает» уже начатые транзакции, а не повторяет бизнес-операцию.

### 7.3. Старт участника
1. Прочитать `<data-dir>/<shardId>/wal.log`. Если файла нет — старт с пустыми балансами.
2. Replay по порядку:
   - `PREPARED` → положить запись в `records`, пересоздать `Reservation` для `DEBIT`;
   - `COMMITTED` → применить операцию к балансам (`DEBIT` уменьшает, `CREDIT` увеличивает), снять `Reservation`, обновить `records`;
   - `ABORTED` → снять `Reservation`, обновить `records`.
3. Для каждой `txId`, оставшейся в `PREPARED` после replay, отправить координатору `STATUS_QUERY(txId)`:
   - decision=COMMIT → выполнить commit + WAL `COMMITTED`;
   - decision=ABORT → выполнить abort + WAL `ABORTED`;
   - decision=UNKNOWN или координатор недоступен → остаться в `PREPARED` (blocking problem).

### 7.4. Корректность через WAL
В WAL участника `COMMITTED <op>` записывается **до** ACK координатору. Поэтому для каждой `COMMITTED` транзакции операция гарантированно есть в логе и replay восстанавливает баланс точно. Для `PREPARED` без финала — replay восстанавливает бронь, после чего `STATUS_QUERY` доносит решение.

## 8. CLI

### 8.1. Пользовательские команды
- `transfer <from> <to> <amount>` — запустить распределенную транзакцию;
- `balance <account>` — баланс счета;
- `clusterDump` — балансы всех шардов и активные брони;
- `setBalance <account> <amount>` — отладочная установка начального баланса;
- `listTransactions` — все известные координатору `txId` со статусами;
- `txLog` — содержимое WAL координатора (читает `coordinator/wal.log`);
- `txLog --participant <nodeId>` — содержимое WAL участника.

### 8.2. Команды для воспроизведения сбоев
Для воспроизведения сценариев нужны два инструмента: детерминированные «crash hooks» и настраиваемые задержки (для ловли тайминга вручную через `kill -9`).

**Управляемое падение (детерминированно):**
- `crashCoordinator <hook>` — координатор сделает `System.exit` при срабатывании указанного хука. Доступные хуки: `after-begin` (после записи BEGIN, до PREPARE), `before-decision` (после получения голосов, до записи DECISION), `after-decision` (после записи DECISION, до broadcast).
- `crashParticipant <nodeId> <hook>` — указанный участник сделает `System.exit`. Хуки: `after-prepared` (после записи PREPARED, до VOTE), `after-committed` (после записи COMMITTED, до ACK).

Crash-флаг живет в памяти процесса до срабатывания и после `System.exit` теряется (так и задумано).

**Настраиваемые задержки (для ручного `kill -9`):**
- `setDelay <component> <hook> <ms>` — вставить sleep на заданном хуке.
  - `component`: `coord` или `<nodeId>`;
  - `hook`: те же `after-begin`, `before-decision`, `after-decision`, `after-prepared`, `after-committed`.

Студент использует `setDelay` чтобы открыть окно (например, 5 секунд между записью DECISION и broadcast), запустить `transfer` и в это окно вручную выполнить `kill -9` процесса.

**Параметры протокола:**
- `setRpcTimeout <ms>` — таймаут RPC между координатором и участниками;
- `setRpcRetries <n>` — число ретраев.

### 8.3. Бенчмарк-команды
- `benchTransfers --shards N --threads T --tx M [--workload <profile>]` — прогнать `M` переводов в `T` потоков; вывести throughput, latency-перцентили, commit/abort ratio.

## 9. Обязательные демонстрационные сценарии

В `demo-scenario.md` должно быть 8 сценариев с копируемыми пошаговыми командами. Сценарии 5–8 включают **реальный kill процесса и его повторный запуск** с тем же `--data-dir`.

### Сценарий 1 — Happy path
`setBalance alice 200`, `setBalance bob 0` → `transfer alice bob 100`. Ожидается decision=COMMIT, балансы `alice=100`, `bob=100`. `txLog` координатора содержит `BEGIN` и `DECISION=COMMIT`. `txLog --participant shardA` содержит `PREPARED` строго перед `COMMITTED`.

### Сценарий 2 — Abort по голосу участника
`setBalance alice 50` → `transfer alice bob 100`. Ожидается VOTE_ABORT от shardA, decision=ABORT, балансы не изменены. В WAL shardA нет записи `COMMITTED` для этой `txId`.

### Сценарий 3 — Abort по таймауту фазы 1
`crashParticipant shardB after-prepared` → `transfer alice bob 100`. shardB записал `PREPARED`, но упал до отправки VOTE. Координатор после ретраев таймаутит и выбирает ABORT (safety-first). shardA получает `ABORT`, бронь снимается. Перезапуск shardB → replay видит `PREPARED` → `STATUS_QUERY` → координатор отвечает `ABORT` → shardB пишет `ABORTED`.

### Сценарий 4 — Потеря COMMIT и ретрай фазы 2
`setDelay coord after-decision 0` (быстро); искусственно «обрубить» одно сообщение COMMIT для shardB через временный сценарий (например, временно остановить shardB между PREPARE и COMMIT, см. ниже). Координатор не получает ACK от shardB, ретраит фазу 2, в итоге доносит COMMIT. Демонстрирует, что фаза 2 идемпотентна и устойчива к потерям.

Реализация: `setDelay shardB after-prepared 5000` → `transfer alice bob 100` → во время задержки на shardB транзакция уже в `PREPARED`, координатор разослал `COMMIT` shardA, попытка отправить shardB упирается в задержку, ретраи; после задержки shardB обрабатывает `COMMIT` нормально.

### Сценарий 5 — Crash координатора после DECISION (durable recovery)
`setBalance alice 200`, `setBalance bob 0` → `crashCoordinator after-decision` → `transfer alice bob 100`. Координатор записал `DECISION=COMMIT` и сделал `System.exit`. Состояние сразу после: shardA или shardB могут быть в `PREPARED` без COMMITTED. `cat data/coordinator/wal.log` показывает `BEGIN` и `DECISION=COMMIT`.

Перезапустить процесс координатора с тем же `--data-dir`. Recovery читает WAL, видит DECISION, досылает COMMIT. Финал: `alice=100`, `bob=100`.

### Сценарий 6 — Blocking problem и safe abort
`crashCoordinator before-decision` → `transfer alice bob 100`. Координатор получил все голоса и упал **до** записи DECISION. На диске координатора только `BEGIN`. shardA в `PREPARED`, держит бронь на `alice 100`. Попытка `transfer alice eve 200` (если у alice нет дополнительных средств) → VOTE_ABORT из-за брони — но координатор-то лежит. `clusterDump` показывает зависшую бронь.

Перезапустить координатор. Recovery видит `BEGIN` без `DECISION` → safe abort: пишет `DECISION=ABORT`, рассылает `ABORT`. Бронь снимается. Подчеркнуть в комментариях: участник **не может** сам выбрать исход — это разрушит атомарность; lock'и могут висеть сколь угодно долго.

### Сценарий 7 — Crash участника после PREPARED (replay + STATUS_QUERY)
`crashParticipant shardA after-committed` → `transfer alice bob 100`. shardA уже записал `COMMITTED` и упал до ACK. Координатор не получает ACK, ретраит COMMIT. Тем временем перезапустить shardA. Replay видит `COMMITTED` → баланс восстановлен корректно (`alice=100`). Повторный `COMMIT` от координатора — no-op + ACK. Транзакция доезжает.

Вариант: `crashParticipant shardA after-prepared` → kill в момент, когда shardA только в `PREPARED`. Координатор уже знает решение и шлет COMMIT, но shardA лежит. Перезапуск: replay видит `PREPARED`, бронь восстановлена, STATUS_QUERY координатору, ответ COMMIT, локальный commit, WAL `COMMITTED`.

### Сценарий 8 — Durability check (replay балансов)
`setBalance alice 1000`, `setBalance bob 0`. Прогнать 50 успешных `transfer alice bob 10` в цикле. Сделать `kill -9` процесса shardA в произвольный момент. Перезапустить shardA. `clusterDump` показывает консистентные балансы для всех завершенных транзакций; для незавершенных (`PREPARED` без финала) бронь восстановлена и снимается через STATUS_QUERY к координатору. Никаких потерянных списаний или дублирований зачислений.

### Способы убить процесс
В сценариях 5–8 «убить процесс» означает:
- либо использовать `crashCoordinator`/`crashParticipant` (детерминированно) — для воспроизводимости;
- либо вручную выполнить `kill -9 <pid>` процесса, предварительно расширив окно через `setDelay` — для гибких экспериментов.

## 10. Бенчмарки и `report.md`

### 10.1. Что измеряем
Базовые метрики каждого прогона:
- `throughputTxPerSec` — успешные транзакции в секунду;
- `avgMs`, `p50Ms`, `p95Ms`, `p99Ms` — end-to-end latency транзакции (от `transfer` до возврата decision);
- `commitRatio`, `abortRatio` — доли COMMIT и ABORT.

Дополнительные метрики (там, где требуется частью):
- `blockedTxCount` — количество транзакций, где хотя бы один участник провел в `PREPARED` дольше N мс;
- `walReplayMs` — время replay WAL при старте;
- `phase1LatencyMs`, `phase2LatencyMs` — разбиение по фазам.

Сохранять в `benchmarks/results.csv`. Колонки минимум:
```
part,scenario,shardCount,threads,totalTx,throughputTxPerSec,avgMs,p50Ms,p95Ms,p99Ms,commitRatio,abortRatio,extraMetric
```

### 10.2. Обязательные прогоны (минимум 11 прогонов)

**Часть A — Scaling по числу участников (3 прогона).** План транзакции вовлекает 2/3/5/15 шардов соответственно (например: чистый перевод A→B; перевод A→B + комиссия на C; перевод A→B + комиссии на C, D, E). `threads=8`, `totalTx=2000`, балансы заведомо достаточны.
Цель: показать, что latency 2PC растет с числом участников (медленный участник диктует темп; больше WAL-синхронизаций).

**Часть B — Abort rate vs. balance distribution (3 прогона).** `shardCount=3`, `threads=8`, `totalTx=2000`, сумма перевода 100. Начальный баланс отправителей: `1000` (10× amount), `100` (1× amount), `50` (0.5× amount).
Цель: показать рост `abortRatio` при недостатке средств; эти ABORT'ы — это VOTE_ABORT, они дешевле COMMIT'ов (нет фазы 2 commit).

**Часть C — Contention на горячем счете (3 прогона).** `shardCount=3`, `threads=16`, `totalTx=2000`, баланс отправителей огромный. Размер пула отправителей: `50`, `5`, `1` (в последнем случае все транзакции списывают с одного счета).
Цель: показать, что reservations создают конкуренцию: при малом пуле многие транзакции пытаются резервировать тот же счет одновременно, рост `abortRatio` и/или latency.
Связать с blocking problem концептуально: если транзакция зависает в `PREPARED`, бронь блокирует следующих.
**Необходимо реализовать thread-safe обработку для демонстрации этого сценария.**

**Часть D — 2PC overhead vs локальная операция (1 прогон, baseline).** Замерить latency «голого» локального CREDIT на одном шарде без 2PC (через прямой RPC к участнику без координатора и фазы prepare).
Сравнить с latency 2PC при `shardCount=2`. Цель: количественно показать стоимость атомарности (минимум 2 RTT и минимум 3 fsync-able записи в WAL).

**Часть E — Recovery time vs объем WAL (2+ прогона).** Загрузить кластер N успешными транзакциями (`N = 100`, `N = 10000`).
Остановить участника, перезапустить, замерить `walReplayMs` до момента готовности обслуживать запросы.
Цель: показать рост startup time линейно от объема WAL. Это мотивация для log compaction (бонус).

### 10.3. Требования к `report.md`
- таблица всех прогонов с колонками выше;
- минимум **5 графиков**: 
  1. throughput и p95 vs `shardCount` (Часть A);
  2. `abortRatio` vs начальный баланс (Часть B);
  3. throughput и/или `abortRatio` vs размер пула отправителей (Часть C);
  4. 2PC vs локальный — гистограмма latency (Часть D);
  5. `walReplayMs` vs `N` (Часть E);
- объяснения trade-offs, минимум следующих:
  - почему latency 2PC растет с числом участников;
  - почему ABORT по голосу дешевле COMMIT;
  - как reservations создают «логическую блокировку» внутри prepare-фазы и что это дает под нагрузкой;
  - почему 2PC принципиально дороже локальной операции;
  - что произойдет с throughput при долгом блокировании участника в `PREPARED`;

## 12. Оценивание

### 12.1. Функциональность — 8 баллов

#### Задача A — Базовая инфраструктура (1.5 балла)
- (0.5) Координатор и ≥3 participant запускаются как **отдельные процессы** с собственными `--data-dir`.
- (0.5) Сетевой слой: TCP, JSON Lines, корректные `requestId`/`txId`, базовые ошибки.
- (0.5) CLI: работают `transfer`, `balance`, `clusterDump`, `listTransactions`, `setBalance`, `txLog`.

#### Задача B — 2PC happy path (1.5 балла)
- (0.5) Phase 1: `PREPARE` рассылается всем, координатор корректно собирает `VOTE` с ретраями и таймаутами.
- (0.5) Phase 2: `COMMIT` только при единогласии, иначе `ABORT`; рассылка с ретраями; safety-first ABORT при таймауте фазы 1.
- (0.5) State machine участника корректна; идемпотентность по `txId` для всех типов сообщений.

#### Задача C — WAL на диске и инварианты (1.5 балла)
- (0.5) WAL координатора: пишутся `BEGIN` и `DECISION` в `<data-dir>/coordinator/wal.log`, формат корректный.
- (0.5) WAL участника: пишутся `PREPARED`, `COMMITTED`, `ABORTED` в `<data-dir>/<shardId>/wal.log`.
- (0.5) Инвариант log-before-reply строго соблюдается; проверяется на защите запуском `tail -f wal.log` параллельно с `transfer` и наблюдением порядка строк.

#### Задача D — Recovery (2.0 балла)
- (0.7) Recovery координатора: после реального `kill -9` или `System.exit` повторный запуск с тем же `--data-dir` корректно дочитывает WAL и досылает решения; `safe abort` для транзакций с `BEGIN` без `DECISION`.
- (0.8) Recovery участника: replay WAL восстанавливает балансы и брони; работает demo durability check (Сценарий 8: 50 транзакций → kill → перезапуск → балансы корректны).
- (0.5) `STATUS_QUERY` от участника после рестарта обрабатывается координатором, шаги после ответа `COMMIT/ABORT/UNKNOWN` корректны.

#### Задача E — Утили для возможности демонстрации сцераиев отказов (0.5 балла)
- (0.3) Управляемые падения через CLI: `crashCoordinator <hook>`, `crashParticipant <nodeId> <hook>` работают для всех заявленных хуков.
- (0.2) Настраиваемые задержки: `setDelay <component> <hook> <ms>` позволяет открыть окно для ручного `kill -9`.\

#### Задача F — Бенчмарки (1.0 балл)
- (1.0) Бенчмарки: ≥11 прогонов в CSV; ≥5 графиков в `report.md`; объяснения trade-offs из §10.3 присутствуют.

### 12.2. Качество кода — 2 балла

#### 1. Дизайн: SOLID / DRY / KISS — 1.0
Конкретные ожидания:
- **SRP:** код WAL не смешан с сетевым слоем и не смешан с бизнес-логикой шарда. Класс координатора не парсит JSON руками внутри своих методов.
- **DIP:** зависимости от инфраструктуры (WAL, сеть) идут через интерфейсы. Например: `interface DurableLog { append(record); readAll(); }`. Это позволяет в тестах подменить файловый WAL на in-memory без правки `Coordinator`/`Participant`.
- **DRY:** общая логика записи WAL и схема событий (BEGIN/DECISION/PREPARED/...) вынесены в один модуль. Сериализация JSON — в одном месте, а не разбросана по обработчикам.
- **KISS:** нет over-engineering. Не вводятся «фабрики стратегий выбора стратегии», абстракции оправданы конкретной потребностью этой ДЗ. Простой код предпочитается «гибкому».

#### 2. Concurrency и читаемость — 1.0
- потокобезопасность: одновременные транзакции на координаторе, одновременные RPC на участнике, одновременная запись в WAL — `synchronized`/`Lock`, нет очевидных гонок и дедлоков;
- таймауты везде, где есть сетевой вызов; нет вечных циклов и зависаний (за исключением намеренного blocking в сценарии 6);
- понятные имена, единый стиль, осмысленные логи: для каждой транзакции видно, в какой фазе она сейчас, какие сообщения отправлены/получены, какие записи в WAL сделаны.
