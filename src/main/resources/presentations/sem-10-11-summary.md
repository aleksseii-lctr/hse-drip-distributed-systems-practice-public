На предыдущих семинарах курса вы уже построили “фундамент” распределённости:

> “Если я только что сделал write, что и где я увижу при read — прямо сейчас, через 50мс, через 500мс, на другой реплике?”

## Терминология

### 1) Consistency
**Модели консистентности** -- видимость наличия данных на нодах и порядок событий над этими данными (read/write) при репликации.

### 2) Consistency vs Isolation — разные оси
- Consistency: про **реплики** (видимость данных на разных узлах).
- Isolation: про **конкурентные транзакции** (аномалии внутри БД) -- на этом не акцентируемся в рамках курса.

- Практический вывод:
- можно иметь отличную изоляцию “внутри шарда”, но eventual между регионами,
- или наоборот: линейризуемый key-value регистр, но без транзакций/изоляции.

### 3) Полезные “рабочие” определения
- **Version (версия)** — метаданные, по которым мы можем сравнить “новее/старее” (integer version, commit timestamp, vector clock).
- **Visibility** — “может ли клиент увидеть запись при чтении”.
- **Staleness** — “насколько старое значение допустимо/вероятно увидеть”.

## От репликации к несогласованности: replication lag
Асинхронная репликация почти всегда означает: есть окно времени, когда:
- лидер уже принял write,
- часть реплик ещё нет,
- чтение может попасть на “старую” реплику.

**Почему это неизбежно в реальном мире:**
- сеть даёт задержки и джиттер,
- ретраи/перепосылки, reordering,

Важно: лаг — не “ошибка”, это естественное свойство async репликации.

## Спектр моделей согласованности
Модели согласованности формируют спектр: сильнее = проще ментальная модель, но дороже по latency/availability.

### Таблица: 4 базовые модели (с примерами “что можно увидеть”)
| Модель       | Что обещает                                                   | Что всё ещё может случиться                             | Интуитивный пример                |
|--------------|---------------------------------------------------------------|---------------------------------------------------------|-----------------------------------|
| Linearizable | read после завершившегося write **обязан** видеть write       | дорого, чувствительно к сетевым проблемам               | “как один сервер”                 |
| Sequential   | есть единый порядок, но не обязательно “по реальному времени” | read может не увидеть write, даже если “по часам” позже | “единая очередь, но не real-time” |
| Causal       | сохраняет причинность (reply не раньше оригинала)             | независимые события могут быть в разном порядке         | “смысловой порядок”               |
| Eventual     | когда‑нибудь реплики сойдутся                                 | stale reads, откаты, конфликты                          | “сходимость без гарантий сейчас”  |

```
┌──────────────────────────────────────────────────────────────────┐
│                    CONSISTENCY SPECTRUM                          │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│ STRONG                                        WEAK               │
│   ↓                                             ↓                │
│                                                                  │
│ ┌─────────────────────────────────────────────────────────────┐ │
│ │ LINEARIZABILITY                                             │ │
│ │ • Total order of all operations                             │ │
│ │ • Real-time guarantees                                      │ │
│ │ • Appears as single copy                                    │ │
│ │ • Examples: Google Spanner, etcd                            │ │
│ │ • Cost: High latency, low availability                      │ │
│ └─────────────────────────────────────────────────────────────┘ │
│                                   ↓                              │
│ ┌─────────────────────────────────────────────────────────────┐ │
│ │ SEQUENTIAL CONSISTENCY                                      │ │
│ │ • All see same order (but not real-time)                    │ │
│ │ • Slower than causal                                        │ │
│ │ • Possible stale reads                                      │ │
│ └─────────────────────────────────────────────────────────────┘ │
│                                   ↓                              │
│ ┌─────────────────────────────────────────────────────────────┐ │

│ │ • Allows temporary inconsistency                            │ │
│ │ • High availability & low latency                           │ │
│ │ • Conflict resolution needed (LWW, Vector Clocks, CRDTs)    │ │
```

## Linearizability (на практике)
### Суть
Если операция A завершилась до начала B в **реальном времени**, B не может “притвориться, что A не было”.

### Как это ощущается в продукте
- “я нажал сохранить и получил OK → в следующем запросе это точно есть”
- “уникальный username действительно уникален” (если всё проверяется линейризуемо)
- “lock/lease реально один”

### Почему дорого
Чтобы поддерживать real-time порядок, обычно нужно:
- лидер + синхронные подтверждения (часто majority),
- или consensus (Raft/Paxos) на log,
- или read barriers (read index), leases (аккуратно) и т.д.

---

## Sequential consistenc 
Sequential говорит: все согласны на один порядок, но этот порядок может не совпасть с реальным временем.

Практический подход:
- в продуктовых системах редко выбирают “чистую sequential” как цель,
- чаще говорят о конкретных гарантиях (bounded staleness, RYW/MR), которые проще продать UX-у.

---

## Causal consistency
Causal даёт важное свойство:
- если B “ссылается” на A (reply, комментарий, правка на основе прочитанного), B нельзя увидеть раньше A.

Но независимые события не заставляет строить в один тотальный порядок (total order).
Отсюда низкая цена по latency.

---

## Eventual consistency
Eventual говорит только: если перестать писать (и когда-нибудь точно станет стабильна), то в итоге все реплики придут к одному состоянию.

Не обещает:
- что вы увидите своё действие сразу
- что лента не откатится
- что конфликты не случатся

Почти всегда eventual дополняют механизмами:
- session guarantees
- quorum read/write
- conflict resolution

## Session guarantees (клиент-центричные гарантии)
Session guarantees — это компромисс: оставить инфраструктуру слабой/быстрой, но сделать UX “как будто всё нормально” для конкретного пользователя.

### Что такое “сессия” в реальном продукте
Сессия может быть:
- один пользователь на одном устройстве,
- одна вкладка,
- один токен авторизации,
- “группа запросов с одним session-id” (sticky in LB).

Важно: гарантия применима только к *тем запросам*, для которых система понимает, что это одна сессия.

---

### RYW — Read Your Writes (ключевая)
**Определение:** если write завершился в сессии, последующий read в той же сессии вернёт это значение или новее.

**Где критично:** посты, email, профиль, “настройки”, банковский UI.

**Паттерны реализации:**
- sticky session,
- session token с minVersion,
- read-from-leader (немасштабируемо, зато надёжно).

---

### MR — Monotonic Reads
**Определение:** если вы уже увидели версию v, вы не увидите меньшую версию в этой же сессии.

**Где нужно:** лента, каталог, счётчики, состояния “включено/выключено”.

**Паттерны:**
- session token: “я не читаю ниже maxSeenVersion”,
- реплика‑selector “не старее X” (если есть метрики lag),
- sticky reads (приклеить чтения к реплике на время).

---

### MW — Monotonic Writes
**Определение:** writes одного клиента применяются в порядке отправки.

**Где нужно:** пошаговые операции, цепочки действий.

**Паттерны:**
- клиентская последовательность записей (sequence на writes на клиенте)
- лидерный лог (если клиент пишет через лидера, порядок проще)

---

### WFR — Writes Follow Reads
**Определение:** если write зависит от прочитанного, система не должна “опубликовать” write без его зависимостей.

**Где нужно:** reply/комментарии, коллаборация, цитаты, “я отредактировал то, что видел”.

**Паттерны:**
- dependency tracking (deps),
- causal metadata (vector clocks/version vectors),
- иногда проще “читать с лидера перед write” в критичных местах.

---

## Практические паттерны реализации гарантий

### Паттерн 1: Sticky sessions
Клиент закреплён за одним узлом:
- + просто,
- – масштабирование/балансировка и failover сложнее.

### Паттерн 2: Session token (version tracking)

Клиент носит “якорь” и отправляет с запросом. Сервер обязан обслужить запрос “не хуже якоря”.

**Ключевой выбор в реализации:**
- ждать ли (bounded wait),
- редиректить ли (на свежую реплику/лидера),
- какой таймаут (UX vs latency).

### Паттерн 3: Read-from-leader / majority
Полезно для:
- денег, прав, заказа,
- любого места, где “не могу показать старое” опасно.

## Причинность: happens-before, vector clocks

Causal/WFR обычно требуют метаданных причинности.

### Как понимать vector clock
- Vector Clock растёт, когда вы делаете write.
- Когда узел получает сообщение/репликацию, он “сливает” вектор по max.
- При сравнении VC можно отличать “раньше/позже” от “конкурентно”.

### Почему VC могут быть дорогими

Размер VC ~ O(numActors/replicas). В больших кластерах это дорого.
Типичные оптимизации/замены (просто знать названия):
- version vectors только по “писателям”,
- Hybrid Logical Clocks (HLC) как практичный компромисс часов + причинности.

---

## Разруливание конфликтов: LWW, multi-value, merge, CRDT
### LWW (last write wins)
Просто, но может “тихо” терять данные. Особенно плохо при скошенных часах.

### Multi-value register (Dynamo-style)
Если два writes конкурентны — хранить обе версии и слить позже.
